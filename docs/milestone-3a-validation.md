# Milestone 3A implementation and validation

Implemented on 2026-09-20. This delivery adds PSU import/export and the shared
save-content import path. Other package formats remain milestones 3B and 3C.
Game-load tests remain milestone 4; no emulator or hardware result is claimed.

## Delivered

- `SaveContent` owns validated directory records and exact file bytes independently
  of a card. Caller-visible buffers are copies. It retains byte-oriented names,
  timestamps, modes, attributes, and opaque record fields, with per-entry
  provenance for any defaulted metadata.
- `MemoryCard.extractSave`, `planImport`, and `importSave` support external saves
  without creating a temporary source card. Imports reuse the existing writer,
  free-space inventory, bad-block exclusions, capacity rules, and candidate
  validation. Existing card-to-card copy logic is unchanged.
- `src/formats/psu.ts` detects PSU from its structure, validates every record and
  payload, and writes a single EMS package. Extensions are not proof of format.
- Per-card Import save opens a review with destination identity, original icon
  preview or fallback, file count, file bytes, allocation requirements, metadata
  notice, and Skip/Replace choice. Import selects the new save and clears a
  search that could hide it. Cancel restores focus to the import button.
- Export save is available for one selected save, even with the inspector hidden.
  Its dialog offers EMS (.psu), then downloads a package without changing card
  bytes, history, or whole-card download status. It works without folder access.
- Session import requires the expected immutable card identity. Closing,
  reopening, editing, or restoring the destination invalidates a stale review.
  Successful imports use the existing one-action Undo and 64 MiB history budget.
- CLI `import-save` and `export-save` use the same engine and format layer.
  Existing files are never overwritten. No dependencies were added.

## Format and metadata policy

PSU contains a 512-byte save-directory record, dot and dotdot records, then one
512-byte record per file and its data padded to a 1024-byte boundary. The entry
count includes the two dot entries. Empty files have no data padding. An empty
save package is valid. The external reference and this implementation support
flat save directories; nested PSU import/export is rejected with alternatives
for a raw folder dump or whole-card download. The common save model and engine
can represent nested saves, but that does not extend the PSU transfer format.

Retain represented metadata, including zero or unusual timestamps, hidden and
copy-protected flags, attributes, and opaque bytes. Normalise allocation and
parent-location fields rather than copying source addresses. Rebuild live
entry counts and allocation for imports. Deleted directory slots and unused
cluster contents are not save-package contents. Export padding is zero-filled;
input padding is ignored. Package byte-for-byte identity is not promised.

PSU supplies full records, so it needs no missing-field defaults. The record
builder for future readers uses fixed 2000-01-01 00:00:00 timestamps, directory
mode 0x8427 or file mode 0x8417, and zero other metadata. Readers must list
synthesised fields in `defaultedFields`; explicit zero values are preserved.
Future formats still require their own mapping and loss policies in 3B.

PSU has no checksum or signature. Structural validation cannot detect every
payload alteration or establish game-specific validity. Trailing bytes,
truncated padding/data, duplicate names, invalid types, and unsupported names
are rejected. Files are never silently truncated or omitted.

## Bounds

- Encoded input/output: 16 MiB. Browser and CLI check input size before reading.
  The decoder checks it again. This permits record/padding overhead above an
  8 MiB card while bounding raw input allocation.
- Combined file bytes and required save allocation: at most 8 MiB each, including
  directory allocation in the latter. Actual destination capacity is tighter and
  is checked with root growth and replacement reclamation included.
- Entry count: at most 16,384, derived from 8 MiB / 512 bytes. A flat PSU directory
  count includes dot entries. Allocation checks further restrict usable counts.
- Names: at most 32 bytes, using the existing card identity rules. No Unicode or
  case normalisation is applied inside a package. Host download filenames are
  sanitised independently. Longer names are rejected rather than truncated.
- Save traversal: depths 0 through 127, matching the card parser after its root
  directory. Counts and lengths are checked before copying payloads.

## Reproduce and try it

```sh
npm ci
npm run check
npm run test:browser
npm run test:reference -- /path/to/mymcplus
npm run dev
```

Open a card, choose Import save, select a PSU package, review it, and import.
Select the save and choose Export save to download a PSU. Save card downloads
the complete edited image. A save with nested directories remains available
for whole-card output or raw dumping, but cannot be exported as PSU.

```sh
npm run card -- import-save destination.ps2 save.psu edited.ps2
npm run card -- import-save destination.ps2 save.psu edited.ps2 replace
npm run card -- export-save edited.ps2 SAVE-DIRECTORY exported.psu
```

## Remaining limits

Only PSU is implemented. Direct ZIP import, multiple packages per action,
standalone conversion without an open card, and other package formats remain
outside 3A. Installed browser/OS picker behaviour and game loads on PCSX2 and
PS2/MemCard PRO2 remain milestone 4 checks. No PS3 compatibility is claimed.
The existing Lucide client-directive and lazy Three.js chunk-size build notices
remain advisories, not build failures.
